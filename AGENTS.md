# Nuclear agent context

Nuclear is a closed-loop payment platform (NFC bands/cards, Apple/Google passes).
Architecture: Cloudflare Workers (TypeScript, Hono) -> Hyperdrive -> PlanetScale PostgreSQL 18.

The owner has authorized agents to keep this file current as the project changes. Update it whenever
a convention, approval rule, secret, migration status or repo layout changes.

## Conventions

- Money: `bigint` integer minor units (USD cents), always JSON numbers bounded far below 2^53. Timestamps: `timestamptz`.
- IDs: `uuid DEFAULT uuidv7()` for anything that can leave the database; `bigint` identity only for an internal-only row that needs one (none today).
- Migrations: plain SQL in `migrations/`, numbered `NNNN_name.sql`. Until the v2 cutover the two v2 files are edited in place (nothing is applied anywhere); after it they are frozen and forward-only. Document every new column or table in docs/TABLES.md at its logical position.
- Financial and authorization reads must not use Hyperdrive query caching.
- Every ID-taking endpoint authorizes by ownership (look up by id AND account), never by id alone.
- Idempotency: one unique `transactions.idem` per attempt, completed or declined, scoped by type: `send:<from account>:<key>`, `pay:<merchant>:<attempt>` (terminal attempts `t:<attempt>`, customer-confirmed `c:<payer>:<key>`), `refund:<merchant>:<key>`, `purchase:<account>:<key>`, `fund:<account>:<key>`, `move:<account>:<key>`, `settle|settle_return|collect:<merchant>:<date>`, `benefit:<run>:<n>`, `claim:<employee row>`. The key is read under the payer's balance lock, so a concurrent retry waits and replays; a repeat that differs is `idempotency_mismatch`.
- Locks: use `FOR NO KEY UPDATE`, never `FOR UPDATE`, on rows that other tables reference (it deadlocks with FK key-share locks). Lock order: tag, original payment, both `balances` rows (ordered by account_id), then the wallet.
- A decline after authority checks is committed as a `declined` transaction with a `status_code` (the API reports it as `failed`); request-validation errors are not recorded. A transaction is immutable: it is never updated, a correction is a new transaction.
- There is no ledger. `transactions` (wallet to wallet, immutable) is the source of truth and balances are checked against what the transactions did (`account_effects`, see "Reconciliation" in docs/TABLES.md). System wallets (fixed ids in `lib/system.ts`): the system account `00000000-0000-7000-8000-000000000001`, Nuclear Bank `...0002` and Nuclear Shop `...0003`; the money functions never update their balance rows. Every organization has an escrow wallet for credit held for employees (docs/ORGANIZATIONS.md).

## Auth model

- Account holder: email + password (scrypt). A session is a **signed 90-day token** (`crypto.ts` `signSession`: sub, sid = the `devices` row, kind owner|wallet, wid, typ = account type). `session.ts` checks the signature with **no database read** for a consumer's owner session on the hot routes only (`LIGHT`: GET balance, activity, wallets, tags; GET one payment or transfer; POST transfers, payments and shop orders); the money functions check the device row inside their own call. Every other route, and every request of a delegated wallet device, a business or an organization, also reads the device row and the account (a primary-key read, no write): a revoked or expired device, a suspended account and a business that is not approved are refused at once. **Accepted risk (owner, 2026-10-23): reads of the signed token keep working after a revoke until the token expires (up to 90 days); there is no revocation denylist.** `POST /v1/auth/refresh` is called at app launch: it rolls the device's expiry 90 days, returns a NEW token (the old one is not invalidated) and the first screen in one answer (account, balance summary, wallets, tags); a revoked or expired device or a suspended account gets 401. Session kinds: `owner` and `wallet` (a delegated shared-wallet device from a 5-minute magic link; `devices.redeemed_at` makes redemption single-use).
- Merchant terminals are not devices. A terminal authenticates with its own HS256 JWT (aud `nuclear:terminal`, own expiry); `terminals.session_token_hash` stores the token's SHA-256 so it is revocable and single-active. Terminal sessions have no owner or wallet powers and only reach `/v1/terminal/*`.
- Admin portal: people sign in with an **Access ID and an access token** (`POST /v1/admin/login {access_id, access_token}`, public), then a code from their authenticator. (Customers' passwords are a separate thing and keep the name "password".) The Access ID is 12 uppercase characters (A-Z, 2-9 without look-alikes, starts with a letter) and always stored/shown uppercase (lowercase input is accepted); the access token is 32 characters (mixed case, digits, `-_.+=`). **Lengths are enforced**: `POST /v1/admin/login` refuses any `access_token` that is not exactly 32 characters with 400 `invalid_request` before touching the database, and the portal limits the Access ID field to 12 characters and the Access Token field to 32 and shows Continue only when both are complete. **The server generates both**: `POST /v1/admin/admins {name}` (any fully signed-in admin, or the operator token) returns `{admin, credentials:{access_id, access_token}}` **once**; only a hash is kept and the token can never be shown again. The portal's Admins page shows them with a download button. `admins.created_by` records who made each admin. Access Tokens are final: there is no forced replacement after sign-in and no change-token endpoint or screen (a lost or leaked token is rotated instead): `POST /v1/admin/admins/:id/rotate-token` (any fully signed-in admin, or the operator) saves a fresh server-generated token (hashed), ends the target's sessions (the caller keeps theirs when rotating their own) and returns the credentials once; the Admins page has a "Rotate Access Token" button per row (opens a modal: confirm, then the new token) and shows the new token masked with Copy and Download. Operators can still use `--reset-token`. Sessions are 8 hours (hashed in `admin_sessions`). Failures are all one answer; 5 wrong tokens or codes lock the account for 15 minutes. Operator-only (scripts): `ADMIN_API_TOKEN=... npm run add-admin -- --name "Jane Doe" [--save file]`, and `npm run manage-admin -- --list | --access-id ID --disable | --enable | --reset-token [--save file] | --reset-mfa`; `--reset-token` generates a fresh token (shown once, or saved to a 0600 file). `GET /v1/admin/me`, `POST /v1/admin/logout`. A wrong *current* token is 401 `invalid_credentials`; only `unauthorized` means the session ended. The operator token still opens the data endpoints and can create/list admins, but cannot change an access token. **Two-step verification (TOTP) is mandatory**: after the token step an admin without it can only call `/me`, `/logout`, `/mfa/setup`, `/mfa/enable` (everything else is 403 `mfa_setup_required`). `POST /mfa/setup` returns the base32 key and `otpauth_uri` (the portal draws the QR code); `POST /mfa/enable {code}` confirms and returns ten single-use recovery codes, shown once. Once enrolled, `POST /login` returns `{mfa_required, mfa_token}` (a 5-minute challenge JWT, not a session) and `POST /login/mfa {mfa_token, code}` takes the 6-digit code or a recovery code. Codes are RFC 6238 (SHA-1, 30 s, ±1 step), each usable once; wrong codes count toward the lock, and a correct token does not reset that count while MFA is pending. `POST /mfa/recovery-codes {code}` replaces the recovery codes. Lost phone: `--reset-mfa`. Admin actions are recorded in `logs` (see "Shop and Audit Log").
- **Email verification and password reset** (`lib/accountMail.ts`, tests `emailauth.e2e.mts`): sign-up emails a verification link (24 h) in the background; the links are **signed tokens with no table** (`signAccountLink`/`verifyAccountLink`; the reset link carries a fingerprint of the current password hash, so using it makes it single-use). `POST /v1/auth/verify-email {token}` (public) sets `accounts.email_verified_at` only if the link's address is still the account's; `POST /v1/auth/verify-email/resend` (signed in, also pending businesses; 3 per hour); `GET /v1/account` returns `email_verified`. `POST /v1/auth/password-reset {email}` always answers 202 (known or not; 3 per email and 10 per IP per hour) and emails a one-hour link; `POST /v1/auth/password-reset/confirm {token, password}` sets the password, signs every device out, lifts a login lock, verifies the email and sends a 'password changed' notice. Nothing is blocked while unverified (owner decision). Links open `APP_URL` for customers, `MERCHANT_PORTAL_URL` for businesses, `ORG_PORTAL_URL` for organizations (`/verify-email?token=`, `/reset-password?token=`); both portals have Forgot password, the reset page, the verify page and a resend row on Profile.
- **System email is OFF (owner, 2026-10-22)**: `EMAIL_FROM` was removed from `wrangler.jsonc` after a failed send hurt the sender reputation, so `sendMail` returns `not_configured`, nothing leaves the system and the text stays in the audit log; restore the var (comment in `wrangler.jsonc`) and deploy to turn it back on, after the sending domain is verified. **System email** (`lib/email.ts`): sent through the Cloudflare `EMAIL` binding from `EMAIL_FROM`. **Addresses on seeded domains (`seed.nuclear.test` and its subdomains) are never sent to**: `sendMail` returns `suppressed`, callers treat that as handled (the monthly claim reminder marks it told so seeded rows never crowd out real ones).
- **Admin view of organizations** (2026-10-22, `lib/orgSupport.ts`, page `organizations` for admin, sales and support, tests `orgadmin.e2e.mts`): `GET /v1/admin/organizations?q=`, `/:id` (profile, wallet, program in words, employee and held totals, runs, Benefits API key hint, document count), `/:id/employees?q=` (no tokens or account ids), `/:id/runs`, `/:id/documents` and a logged download, `/:id/activity`; `PUT /:id/status` (admin only) suspends or reactivates (sign-in, the Benefits API key and the Fixed Benefits scheduler all stop; the scheduler now skips non-active organizations). Admin portal: Organizations list and a detail page with Details, Employees, Benefit Runs, Documents and Activity tabs; no approval step (organizations are active at once).
- Handles (`accounts.handle`, 4-12 lowercase alphanumeric, unique, nullable) can be set or changed only by the primary account's own owner session.

## Domain rules worth remembering

- Daily counters (`wallets.spent_today`, `products.sold_today`, the cap numbers on `balances`) roll themselves: see "Self-rolling counters" below.
- **Wallet balance (earmarked funds)**: `wallets.balance` NULL = the wallet spends from the account's shared funds (default and person wallets); a number = money the owner set aside, a **hard limit**: the wallet spends and sends only up to it (no credit) with no other approval, and the rest of the account cannot spend it. Spendable for an unearmarked wallet = account balance minus everything earmarked (plus approved credit for payments). Agent wallets are created at 0 (pass `balance: null` to share, or a number to fund). Owner endpoints: `PUT /v1/wallets/:id/balance {balance: number|null}` (raise needs enough shared funds, else 422 `insufficient_shared_balance` with `available`; null releases), `GET /v1/wallets/:id/allocations` (history from `logs`, also for that wallet's delegated session), wallet creation accepts `balance`. Declines are `wallet_balance_exceeded`. Incoming sends and refunds to an earmarked wallet raise its balance; closing releases it. `GET /v1/balance` adds `earmarked` and its `available_to_*` are the shared funds (a delegated session on an earmarked wallet sees that wallet's balance). Earmarks are not transactions (balances stay account-level); every change is a `wallet.earmark` row in `logs` (`earmarkLog`); stats reconciliation reports `earmarks_within_balances`. Money movements lock balances, then the wallet, so concurrent spends cannot overdraw a wallet.
- **Agent keys and MCP**: an agent wallet (type `agent`) has one API key, **created together with the wallet** (the `POST /v1/wallets` response for an agent includes `key` once, as `nk_agent_<43 chars>`); `POST /v1/wallets/:id/key` (owner only) rotates it later (old key dies at once) and returns the new one once; `DELETE /v1/wallets/:id/key` revokes; only the SHA-256 is stored; the wallet JSON shows `key: {hint, last_used_at}`; closing the wallet clears it, suspending it stops it working. A key is a bearer token with session kind `agent`: it behaves like a delegated wallet session for its wallet only (balance, activity, handle/recipient lookup, transfers, customer-confirmed payments, own tags) and is refused (403) on wallet management, devices, logout, account, shop orders and everything owner-only. The earmarked wallet `balance` is its hard spending limit. The `nuclear-mcp` Worker (apps/mcp) speaks MCP over Streamable HTTP at `/mcp` (POST only, JSON responses, `Authorization: Bearer nk_agent_...`), holds no secrets and no database access, and forwards the key to nuclear-api through a service binding. Tools: `get_wallet`, `lookup_recipient` (handle or email), `send_money`, `pay_merchant` (terminal_id + amount, or checkout_id) and `list_activity`; sends and payments require an `idempotency_key`. Agents cannot create wallets, change limits or manage keys. Not built: an owner screen for keys, per-transaction caps, recipient allow-lists.
- **Rate limits** (all in `lib/throttle.ts` `RULES`, kept in a Durable Object `RateLimiter` (binding `LIMITER`, class exported from `src/worker.ts`; an in-memory limiter per isolate when unbound, for tests; limiter errors fail open); fixed windows that start at the first hit, answers `429 {error: "rate_limited", retry_after}` plus a `Retry-After` header; the daily cron sweeps old windows): customer login 5 wrong passwords per email per 15 minutes (known or unknown email alike, the right password is refused while locked, a good login clears it) and 30 attempts per IP per minute; signup 10 per IP per hour; admin sign-in and MFA 20 per IP per minute; magic-link redeem 20 per IP per minute; recipient lookup by email 30 per account per hour; handle lookup 60 per account per minute; tag claim 20 per account per hour; shop orders 10 per account per minute; agent keys 120 requests per minute per key and 30 sends/payments per minute per key (the MCP returns `rate_limited` with `retry_after_seconds`). IP limits use `cf-connecting-ip` and are skipped when it is absent (local runs and tests). Not limited: owner sessions generally, terminals.

- Sends: funded balance only, never credit; same-account and business recipients are rejected.
- Payments: balance first, then approved credit; the credit part is `credit_amount` on the pay transaction (refunds restore it first). A tag tap within wallet and tag limits is authorized (no step-up). Every verified tag tap burns its proof: the counter must advance and is consumed atomically with the outcome, even when declined, unassigned or locked (`app_pay_tap` does it in the same call). - Refunds (`app_refund`, `app_refund_resolve`; table `refunds` for requests): against a completed payment, bounded by what is unrefunded minus pending (reserved) refunds (original row locked). The merchant balance may go negative; credit drawn by that payment is restored first. One create route, `POST /v1/terminal/refunds`:
  - terminal `allow_refunds = true` and no tap: refunds now, approver = the merchant.
  - a tap by merchant staff with role `write`: refunds now, the transaction's `account_id` = that account and `meta.approved` (the proof is burned with the refund; the POS sends the tap straight here, not via lookup).
  - no tap on an approval-required terminal, or a tap by someone who is not write staff: recorded as a **pending request** in `refunds` (202, `status_code: awaiting_approval`). Nothing moves, no transaction exists yet, the customer does not see it, and its amount stays reserved. Pending refunds never expire; they stay until approved or rejected.
  - approving writes the refund transaction **under the request's id** and moves the money; rejecting closes the request (reported as a failed refund with code `rejected`). Resolve from the terminal (`GET /v1/terminal/refunds?status=pending`, `POST /v1/terminal/refunds/:id/approve|reject` with a write-staff tap) or the merchant owner (`GET /v1/refunds`, `POST /v1/refunds/:id/approve|reject`; the owner's account is the approver). Approve/reject are idempotent.
  - a tap that cannot be resolved (garbage, unknown, unassigned, locked, replayed) is an error, not a pending request.
- Orders: a **checkout** is an open payment request (`checkouts`, `items` a JSON snapshot of names and prices). - **Settlement and payouts** (`lib/settlement.ts`, `lib/ach.ts`, tests `settlement.e2e.mts`): once a day (the cron, after midnight New York; the second cron of the night finds `system.settled_day` done and does nothing) every **active merchant with an active payout bank** is settled for its WHOLE net balance, one `settlements` row per merchant per day (unique on date + merchant). A positive net is a payout (`direction = 'credit'`): the balance drops at once (so later sales belong to the next day and the money can never be paid twice) and a `settle` transaction goes from the merchant's wallet to Nuclear Bank (key `settle:<merchant>:<date>`). A negative net is a collection (`debit`): **nothing moves until the bank confirms**, and collections in flight count against the debt so it is never collected twice. The bank's answer finishes the row (`settled`/`returned`): payout returned = a `settle_return` transaction restores the balance; collection settled = a `collect` transaction credits the balance; collection returned = the debt stands and is collected again next run. A batch the bank refuses fails the day (`failed`) and gives every payout back. A run that stopped half way is finished by the next call (the per-merchant row and key stop double settlement); a missed cron just means the next run's net covers everything. Merchants without a bank, suspended or pending are skipped (money waits). The rail is the `AchProvider` seam in `lib/ach.ts` (items are the `settlements` rows, `itemId`): **no ACH provider is chosen**, only the sandbox adapter exists (used when `SANDBOX_FUNDING` is on; it settles every item at the first poll); with no provider the job does nothing. A real adapter will read account numbers with the audited `revealBank()`. Admin (a "run" is the group of rows for a date and its id is the date): `GET /v1/admin/settlements`, `GET /v1/admin/settlements/<date>` (Transactions page roles), `POST /v1/admin/settlements/run` and `POST /v1/admin/settlements/<date>/confirm` (admin only, logged). `GET /v1/business/payouts` lists a merchant's rows. - **Money moves are SQL functions** (docs/SCHEME-V2.md, section 6; `migrations/0002_money_functions.sql`; called from TypeScript with `callMoney` in `lib/txn.ts`, one plain statement = its own transaction): `app_send` (`lib/send.ts`), `app_pay_app` / `app_pay_tap` (`routes/payments.ts`), `app_refund` / `app_refund_resolve` (`lib/refund.ts`) and `app_purchase` (`lib/shop.ts`). Each locks the balance rows (stable order) and the wallet, reads the idempotency key under those locks, applies every rule, and writes either the completed transaction with its balance changes or a `declined` transaction, returning json; the lock is held for the milliseconds the function runs instead of across network round trips (a send, an app payment and a refund are ONE statement in all: `tests/roundtrips.e2e.mts` counts them). The rules live in SQL in exactly these functions; everything else (benefit runs, claims, moves, fundings, settlement) stays in TypeScript with batched statements (`Promise.all` inside `sql.begin`, which postgres.js pipelines on one connection). **Rules for new code**: a new money path that is hot (a payment, a send) becomes a function with focused tests; never `await` independent statements one after another inside a money transaction; do not use `Promise.all` on the pool outside a transaction; look up wallets inside the transaction; pass amounts to a function as JSON numbers (they are bounded far below 2^53) and give a function its `device` so a revoked session cannot move money. If two calls race to write one key with different lock orders the loser gets a unique violation (23505) and `callMoney` calls again, which replays. Lock order: tag, checkout, products (by id), balances (by account id), wallet; organizations lock their own balances row first. `tests/moneyedge.e2e.mts` (30 send and pay edge cases) and `tests/concurrency.e2e.mts` (80 concurrent payments and sends across 6 payers and 2 merchants: no deadlock, money conserved, one charge for five simultaneous retries) are the contract. Set `globalThis.__sqlTrace` in a test to count the statements a request sends.
