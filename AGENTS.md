# Nuclear agent context

Nuclear is a closed-loop payment platform (NFC bands/cards, Apple/Google passes).
Architecture: Cloudflare Workers (TypeScript, Hono) -> Hyperdrive -> PlanetScale PostgreSQL 18.

The owner has authorized agents to keep this file current as the project changes. Update it whenever
a convention, approval rule, secret, migration status or repo layout changes.

## Conventions

- Money: `bigint` integer minor units (USD cents), always JSON numbers bounded far below 2^53. Timestamps: `timestamptz`.
- IDs: `uuid DEFAULT uuidv7()` for anything that can leave the database; `bigint` identity only for internal-only rows (`ledger_entries`).
- Migrations: plain SQL in `migrations/`, numbered `NNNN_name.sql`, forward-only. New columns are documented in docs/TABLES.md at their logical position; if that differs from the physical end of the table, a later migration rebuilds the table in documented order (see 0013).
- Financial and authorization reads must not use Hyperdrive query caching.
- Every ID-taking endpoint authorizes by ownership (look up by id AND account), never by id alone.
- Idempotency: sends and refunds are unique per (type, source account, key); payments per (merchant, key). Terminal attempts are stored as `t:<attempt>`, customer-confirmed payments as `c:<payer account>:<key>`.
- Locks: use `FOR NO KEY UPDATE`, never `FOR UPDATE`, on rows that other tables reference (it deadlocks with FK key-share locks). Lock order: tag, original payment, both `balances` rows (ordered by account_id), then the wallet.
- A decline after authority checks is committed as a `failed` transaction with a `status_code`; request-validation errors are not recorded.
- Ledger is append-only and balanced per posting event (deferred trigger). Buckets: `funded_balance`, `credit_receivable`, `pending_funding`, `bank_settlement`, `platform_clearing`, `employee_escrow` (employer credits held for employees who have not claimed; see docs/ORGANIZATIONS.md). Benefits wallets are attributed with `ledger_entries.wallet_id` on `funded_balance` lines.

## Auth model

- Account holder: email + password (scrypt), session in `devices` (hashed token, rolling 90 days). Session kinds: `owner` (devices.wallet_id NULL) and `wallet` (delegated shared-wallet device from a 5-minute magic link).
- Merchant terminals are not devices. A terminal authenticates with its own HS256 JWT (aud `nuclear:terminal`, own expiry); `terminals.session_token_hash` stores the token's SHA-256 so it is revocable and single-active. Terminal sessions have no owner or wallet powers and only reach `/v1/terminal/*`.
- Admin portal: people sign in with an **Access ID and an access token** (`POST /v1/admin/login {access_id, access_token}`, public), then a code from their authenticator. (Customers' passwords are a separate thing and keep the name "password".) The Access ID is 12 uppercase characters (A-Z, 2-9 without look-alikes, starts with a letter) and always stored/shown uppercase (lowercase input is accepted); the access token is 32 characters (mixed case, digits, `-_.+=`). **Lengths are enforced**: `POST /v1/admin/login` refuses any `access_token` that is not exactly 32 characters with 400 `invalid_request` before touching the database, and the portal limits the Access ID field to 12 characters and the Access Token field to 32 and shows Continue only when both are complete. **The server generates both**: `POST /v1/admin/admins {name}` (any fully signed-in admin, or the operator token) returns `{admin, credentials:{access_id, access_token}}` **once**; only a hash is kept and the token can never be shown again. The portal's Admins page shows them with a download button. `admins.created_by` records who made each admin. Access Tokens are final: there is no forced replacement after sign-in and no change-token endpoint or screen (a lost or leaked token is rotated instead): `POST /v1/admin/admins/:id/rotate-token` (any fully signed-in admin, or the operator) saves a fresh server-generated token (hashed), ends the target's sessions (the caller keeps theirs when rotating their own) and returns the credentials once; the Admins page has a "Rotate Access Token" button per row (opens a modal: confirm, then the new token) and shows the new token masked with Copy and Download. Operators can still use `--reset-token`. Sessions are 8 hours (hashed in `admin_sessions`). Failures are all one answer; 5 wrong tokens or codes lock the account for 15 minutes. Operator-only (scripts): `ADMIN_API_TOKEN=... npm run add-admin -- --name "Jane Doe" [--save file]`, and `npm run manage-admin -- --list | --access-id ID --disable | --enable | --reset-token [--save file] | --reset-mfa`; `--reset-token` generates a fresh token (shown once, or saved to a 0600 file). `GET /v1/admin/me`, `POST /v1/admin/logout`. A wrong *current* token is 401 `invalid_credentials`; only `unauthorized` means the session ended. The operator token still opens the data endpoints and can create/list admins, but cannot change an access token. **Two-step verification (TOTP) is mandatory**: after the token step an admin without it can only call `/me`, `/logout`, `/mfa/setup`, `/mfa/enable` (everything else is 403 `mfa_setup_required`). `POST /mfa/setup` returns the base32 key and `otpauth_uri` (the portal draws the QR code); `POST /mfa/enable {code}` confirms and returns ten single-use recovery codes, shown once. Once enrolled, `POST /login` returns `{mfa_required, mfa_token}` (a 5-minute challenge JWT, not a session) and `POST /login/mfa {mfa_token, code}` takes the 6-digit code or a recovery code. Codes are RFC 6238 (SHA-1, 30 s, ±1 step), each usable once; wrong codes count toward the lock, and a correct token does not reset that count while MFA is pending. `POST /mfa/recovery-codes {code}` replaces the recovery codes. Lost phone: `--reset-mfa`. Admin actions are recorded in `logs` (see "Shop and Audit Log").
- Handles (`accounts.handle`, 4-12 lowercase alphanumeric, unique, nullable) can be set or changed only by the primary account's own owner session.

## Domain rules worth remembering

- Daily reset of `wallets.spent_today` and `products.sold_today` at 00:00 America/New_York: see "Daily reset" below (cron plus a request-time catch-up).

- **Wallet balance (earmarked funds)**: `wallets.balance` NULL = the wallet spends from the account's shared funds (default and person wallets); a number = money the owner set aside, a **hard limit**: the wallet spends and sends only up to it (no credit) with no other approval, and the rest of the account cannot spend it. Spendable for an unearmarked wallet = account balance minus everything earmarked (plus approved credit for payments). Agent wallets are created at 0 (pass `balance: null` to share, or a number to fund). Owner endpoints: `PUT /v1/wallets/:id/balance {balance: number|null}` (raise needs enough shared funds, else 422 `insufficient_shared_balance` with `available`; null releases), `GET /v1/wallets/:id/allocations` (history, also for that wallet's delegated session), wallet creation accepts `balance`. Declines are `wallet_balance_exceeded`. Incoming sends and refunds to an earmarked wallet raise its balance; closing releases it. `GET /v1/balance` adds `earmarked` and its `available_to_*` are the shared funds (a delegated session on an earmarked wallet sees that wallet's balance). Earmarks post nothing to the ledger (balances stay account-level) and are logged in `wallet_allocations`; stats reconciliation reports `earmarks_within_balances`. Money movements lock balances, then the wallet, so concurrent spends cannot overdraw a wallet.
- **Agent keys and MCP**: an agent wallet (type `agent`) has one API key, **created together with the wallet** (the `POST /v1/wallets` response for an agent includes `key` once, as `nk_agent_<43 chars>`); `POST /v1/wallets/:id/key` (owner only) rotates it later (old key dies at once) and returns the new one once; `DELETE /v1/wallets/:id/key` revokes; only the SHA-256 is stored; the wallet JSON shows `key: {hint, last_used_at}`; closing the wallet clears it, suspending it stops it working. A key is a bearer token with session kind `agent`: it behaves like a delegated wallet session for its wallet only (balance, activity, handle/recipient lookup, transfers, customer-confirmed payments, own tags) and is refused (403) on wallet management, devices, logout, account, shop orders and everything owner-only. The earmarked wallet `balance` is its hard spending limit. The `nuclear-mcp` Worker (apps/mcp) speaks MCP over Streamable HTTP at `/mcp` (POST only, JSON responses, `Authorization: Bearer nk_agent_...`), holds no secrets and no database access, and forwards the key to nuclear-api through a service binding. Tools: `get_wallet`, `lookup_recipient` (handle or email), `send_money`, `pay_merchant` (terminal_id + amount, or checkout_id) and `list_activity`; sends and payments require an `idempotency_key`. Agents cannot create wallets, change limits or manage keys. Not built: an owner screen for keys, per-transaction caps, recipient allow-lists.
- **Rate limits** (all in `lib/throttle.ts` `RULES`, counters in the `throttles` table, fixed windows that start at the first hit, answers `429 {error: "rate_limited", retry_after}` plus a `Retry-After` header; the daily cron sweeps counters older than a day): customer login 5 wrong passwords per email per 15 minutes (known or unknown email alike, the right password is refused while locked, a good login clears it) and 30 attempts per IP per minute; signup 10 per IP per hour; admin sign-in and MFA 20 per IP per minute; magic-link redeem 20 per IP per minute; recipient lookup by email 30 per account per hour; handle lookup 60 per account per minute; tag claim 20 per account per hour; shop orders 10 per account per minute; agent keys 120 requests per minute per key and 30 sends/payments per minute per key (the MCP returns `rate_limited` with `retry_after_seconds`). IP limits use `cf-connecting-ip` and are skipped when it is absent (local runs and tests). Not limited: owner sessions generally, terminals.
- **Daily reset** (`lib/dailyReset.ts`, `lib/cron.ts`, tested in `cron.e2e.mts`): `wallets.spent_today` and `products.sold_today` are zeroed once per program day (America/New_York). The `daily_reset_day` row of the `system` table records the last day done; `ensureDay(sql, day)` lets the first caller on a new day win the row and reset in the same transaction, and everyone else does nothing. Callers: the cron (04:00 and 05:00 UTC, which bracket midnight in summer and winter; neither run looks at the clock, each just asks for its own New York date) and, **as the backstop for a missed cron, the first request to any route that reads or changes the counters** (`/transfers`, `/payments`, `/terminal/payments`, `/terminal/products`, `/shop/orders`, `/wallets`), via the `programDay` middleware: one cheap read per request normally. Several missed days are one reset; concurrent requests at the rollover cause one reset and lose no spend; a cron that fires after a request already reset the day wipes nothing. Both cron runs also sweep old rate-limit rows. To check the cron on the live system: `select key, value from system` shows `daily_reset_day` (the new date shortly after 00:00 New York) and `cron_last_run` (the time of the last cron run, written by every run).
- Sends: funded balance only, never credit; same-account and business recipients are rejected.
- Payments: balance first, then approved credit; credit portion is journaled on the payment. A tag tap within wallet and tag limits is authorized (no step-up). Every verified tag tap burns its proof: the counter must advance and is consumed atomically with the outcome, even when declined, unassigned or locked. That includes tap lookup (`POST /v1/terminal/lookup`, which returns `account.{account_id, wallet_id, handle, display_name, photo, staff}`), so a tap used for lookup cannot also authorize a payment or refund.
- Pass (Apple/Google) taps on terminals return 501 until reader certification; passes pay through the customer-confirmed path `POST /v1/payments` (requires `terminal_id`).
- Refunds: against a completed payment, bounded by what is unrefunded minus pending (reserved) refunds (original row locked). The merchant balance may go negative; credit drawn by that payment is restored first. One create route, `POST /v1/terminal/refunds`:
  - terminal `allow_refunds = true` and no tap: refunds now, approver null.
  - a tap by merchant staff with role `write`: refunds now, `approved_by_account_id` = that account (the proof is burned with the refund; the POS sends the tap straight here, not via lookup).
  - no tap on an approval-required terminal, or a tap by someone who is not write staff: recorded as a **pending** refund (202, `status_code: awaiting_approval`). Nothing moves, no ledger lines, the customer does not see it, and its amount stays reserved. Pending refunds never expire; they stay until approved or rejected.
  - resolve pending refunds from the terminal (`GET /v1/terminal/refunds?status=pending`, `POST /v1/terminal/refunds/:id/approve|reject` with a write-staff tap) or the merchant owner (`GET /v1/refunds`, `POST /v1/refunds/:id/approve|reject`; the owner's account is the approver). Approve/reject are idempotent.
  - a tap that cannot be resolved (garbage, unknown, unassigned, locked, replayed) is an error, not a pending request.
- Orders: every payment settles a **checkout** (`checkouts` + `checkout_items`, prices and names snapshotted). Create one with `POST /v1/terminal/checkouts {items | amount, reference?, expires_in?}`, then pay it by tap (`POST /v1/terminal/payments {checkout_id, credential}`) or in the customer's app (`POST /v1/payments {checkout_id}`; `GET /v1/checkouts/:id` is the customer's preview). The old one-step bodies (`amount`/`items` on the payment) still work and create the checkout inside the same transaction; a declined one-step payment cancels it, a declined payment of an existing checkout leaves it open. `checkout_id` cannot be combined with `amount`/`items`.
- Stock is taken at payment (never at checkout creation): in the same transaction as a *completed* payment, tracked stock is decremented and `total_sold`/`sold_today` incremented; reaching 0 flips `status` to `sold_out` (DB trigger). Cart and checkout problems (sold out, not enough, inactive, not open, expired) are returned before the tap is consumed; a stock race lost after the tap is a recorded `declined` payment with no money moved. A retry of a recorded attempt returns the recorded result and does not re-price. Lock order: tag, checkout, products (by id), balances, wallet; refunds restock products before touching balances.
- Restock on the terminal: `POST /v1/terminal/products/:id/restock {quantity, expected_stock?}` (increments; untracked products refused). Terminal catalogue list: `GET /v1/terminal/products`.
- Item refunds: refund `mode: "items"` with `items: [{checkout_item_id, quantity}]` and `restock` (default **false**: send `restock: true` to put the units back on the shelf). Amount = snapshot net price x quantity. Per-line state is on `checkout_items` (`refunded_quantity`, `refund_pending_quantity`, kept in step under the original payment's row lock: pending reserves, completing moves to refunded, rejecting releases). The refund transaction carries `checkout_id` and a small `items` JSON of the lines it covers (its own record for approval/audit); there is no refund-items table. Units go back on the shelf only when `restock` is true and the refund completes. `full`/`partial` amount refunds never touch items or stock. `GET /v1/terminal/payments/:attempt` returns the order's items with `refundable_quantity` for building an item refund.
- Orbs register on claim: `PUT /v1/terminal/orb {uid, model, software}` (or the owner's `PUT /v1/terminals/:id/orb`). `uid` is the Orb's MAC address (any separators/case, normalized to 12 uppercase hex); `id` stays a generated UUID. The terminal reads uid/model/firmware over BLE; an unknown uid creates the row owned by the claimer. One Orb per terminal: pairing moves it off its previous terminal and unpairs the terminal's previous Orb; an Orb owned by another account returns 409; re-pairing records the reported firmware. `PATCH /v1/terminal/orb {software}` reports a firmware update; `POST /v1/orbs/:id/release` (owner) frees an Orb so another account can claim it. No Orb rows are pre-loaded.

- **Money transactions hold row locks for about three round trips** (2026-10-19, from PlanetScale's weekly report: `balances ... for no key update` p99 1.5 s, `tag_models ... for no key update` p99 5.3 s on a 1/16 vCPU PS-5): inside `sql.begin`, independent statements are sent together with `Promise.all([tx`...`, tx`...`])` (postgres.js pipelines them on the transaction's one connection and the server runs them in the order sent, so lock order is unchanged), so `payCore`, `sendFunds` and `purchase` do: insert the attempt, ONE batch of reads (balance rows locked first in stable order, wallet lock, account statuses, earmarked total, recipient's incoming-today), the decision, ONE batch of writes (balances, wallet counters and earmark in one `update`, ledger lines, transaction completed), commit. Lock order is now balances, wallet, then (purchases only) the product. **Rules for new code**: never `await` independent statements one after another inside a money transaction; do not use `Promise.all` on the pool outside a transaction (each query would take its own connection; Workers allow few); look up wallets inside the transaction. Portal: an **Email Merchant** button on the merchant page (active or pending) and an **Email Merchants** button on the Merchants list open a compose window with five template cards (Welcome, Documents needed, Under review, Approved, Action required) and Custom; the list version picks an audience (with counts) and asks for a confirm before sending; Sales has no button.
- **Images (R2)**: the bucket `nuclear-images` (binding `IMAGES`) holds **tag pictures, store (shop) pictures, account photos, wallet photos and product images**; the bucket `nuclear-uploads` (binding `UPLOADS`, private) holds every other document (business documents today). The database stores only the **R2 key** of an image (`tags/`, `shop/`, `accounts/`, `wallets/` or `products/` + `<id>-<epoch ms>.<png|jpg>`; a CHECK on every `photo` column enforces it), never a URL or a bare file name. **The API always builds the full URL** when it returns a photo (`imageUrl()` in `lib/images.ts`: `<PUBLIC_URL, else the request's address>/v1/photos/<key>`; `PUBLIC_URL` is set to https://nuclear-api.a-space.workers.dev in wrangler.jsonc), so apps use `photo` as is (null = no photo). `GET /v1/photos/:folder/:file` serves any key publicly with an immutable cache (names are unguessable, so a photo is private only by obscurity). Tag and shop pictures are PNG (256 KB max, the portal resizes to 256 x 256); account and wallet photos are 256 x 256 JPEG. A new upload gets a new key and the old object is deleted. The old `/v1/shop/models/:id/photo` and `/items/:id/photo` routes are gone.
- **Shop and Audit Log (admin)**: `GET/POST /v1/admin/shop-items`, `GET/PATCH /v1/admin/shop-items/:id`, `PUT .../photo` (page `shop`: Admin and Sales write, others with the page read). `GET /v1/admin/logs?who=&action=&q=&cursor=&limit=` (page `audit`: Admin only), `GET /v1/admin/users/:id/activity` and `/merchants/:id/activity` (newest first, cursor `<ts>|<id>`; a person's activity = rows targeting them, done by them, or carrying their `account_id`/`merchant_id` in details). `logs` rows are written by `lib/audit.ts` (`adminLog`, `customerLog`; failures never break the action): admin sign-out, MFA, create/role/token changes, user and wallet suspend, sign-out, unlock, key revoke, merchant suspend, refund approve/reject, terminal sign-out, tag model create/update/photo/import, shop item create/update/photo; customer sign-up, login, failed login, logout, handle change, device revoke, agent key rotate/revoke. Portal: Shop and Logs pages in the navigation, an Activity tab on users and merchants, an item/type pill in the user Orders tab.
- **Admin roles** (`lib/roles.ts` is the one place; `admins.role`; the operator token counts as admin): `admin` (every page incl. Admins; the only role that creates admins, rotates tokens and changes roles), `accounting` (Overview, Transactions), `sales` (Users, Merchants, Tags read-only, Shop), `support` (Users, Transactions; scope chosen by us, change it in `ROLE_PAGES`), `tags` (Tags only, may change tags) and `merchants` (Merchants only). Every role keeps its own Security page. The sign-in answer and `GET /v1/admin/me` carry `role`, `pages` and `landing` (the role's first page: where it lands after sign-in); the portal shows only those pages, redirects any other address to the landing page, and hides Add/Edit/Provision on tags for read-only roles. API enforcement is per route (`403 forbidden_role`): stats = overview; merchants; users; transactions; tag-models read = tags page, write = admin or tags; `/admins*` = admin only. `POST /v1/admin/admins {name, role}` (role defaults to admin); `PUT /v1/admin/admins/:id/role {role}` (admin or operator; nobody changes their own role; effective on the next request, no new sign-in). Scripts: `add-admin --role`, `manage-admin --role`. The Admins page shows a ROLE column (replacing Two-step) and a Change Role modal.
- **Merchant support page** (`/merchants/<id>`, opened from the Merchants list; tabs are `?tab=terminals|staff|transactions|products`, Details is the default; everything comes from existing tables, no schema of its own): five top cards: Profile (the same 128 x 128 photo, handle and plan card as on the user page), Balance, Payments (lifetime and today), Refunds (and declined payments), Awaiting Approval (pending refunds, customers, last payment); tabs Details (business, legal name, handle, contact, address, website, payout bank last four only, IDs), Terminals (refund permission, signed in or out, paired Orb with model, uid and firmware, volume, last payment; no payment count column), Staff (name, email, role, bank last four), Transactions (the merchant's payments and refunds with customer, terminal, via, reference, status code and approver; All / Payments / Refunds / Awaiting Approval cards with counts; the same Period select and totals) and Products (category, price, stock, sold today and total, status, visibility). Needs the Merchants page (admin, sales, merchants). API: `GET /v1/admin/merchants/:id`, `/terminals`, `/staff`, `/products`, `/transactions?kind=all|payments|refunds|pending&from&to&cursor&limit` (404 for anything that is not a business account). The one write is the support action `POST /v1/admin/terminals/:id/sign-out` (clears the terminal's stored session so its token stops working at once; roles `admin` and `merchants` only, `MERCHANT_WRITERS` in `lib/roles.ts`; Sales and others get 403). **Admin-only actions** (`MERCHANT_ADMINS` = admin, plus the operator token): `POST /v1/admin/merchants/:id/refunds/:refundId/approve|reject` resolves a pending refund (approving moves the money now, rejecting releases the reservation; idempotent; 404 for another merchant's refund, 422 `refund_not_pending`) and `PUT /v1/admin/merchants/:id/status {status: "active"|"suspended"}` suspends or reactivates a merchant (a suspended merchant takes no payments, its owner sessions and its terminals are refused on their next request, since every request re-checks the account; nothing is deleted). With no audit table, a refund resolved from here carries `transactions.provider_reference` = `admin:<ACCESS ID>` (or `operator`) and the merchant Transactions tab shows it as "approved by Admin <ID>"; suspensions are logged in `logs`. The merchant page shows Suspend/Reactivate Merchant and Approve/Reject (each behind a confirm modal) only to Admin. Transaction tables (this page and the main Transactions page) centre rows vertically, show the date small, tint failed rows very light pink (refund rows light yellow, funding rows light green; failed wins) and print the reason code (`status_code`, no label) on its own line at the right of the Status cell.
- **User support page** (`/users/<id>`, opened from the Users list; `?tab=wallets|transactions|tags|devices|funding|orders`, Details default; existing tables only): five top cards: Profile (a 128 x 128 photo, initials when there is none, with the handle and the plan stacked under it; `photo` comes from `accounts.photo` when it is an image address), Balance (shared vs earmarked, credit), Sent and Paid, Received and Loaded, Activity (today, failed attempts, last activity); tabs Details (contact, handle, pending loads, whether the login is locked, IDs), Wallets (type, status, earmarked spendable balance or "Shared funds", daily limit and spent today, pay/send permissions, agent key hint and last use), Transactions (everything the account took part in with signed amounts, counterparty, wallet, via, agent flag; All / Sends / Received / Payments (pay and store purchase) / Loads / Refunds cards with counts; Period select and money out/in totals; not shown: refund requests still waiting for the merchant and failed attempts other people made towards this person), Tags (model, label, wallet, locked, per-tap limit; never the NFC UID), Devices (every session: platform, shared wallet, started, last used, active/signed out/expired; never a token), Funding (loads with status and failure code, linked banks by last four) and Orders (store orders with city only). Needs the Users page (admin, sales, support). API: `GET /v1/admin/users/:id` and `/wallets`, `/tags`, `/devices`, `/funding`, `/orders`, `/transactions?kind=all|sends|received|payments|loads|refunds&from&to&cursor&limit` (404 for anything that is not a consumer account). **Support actions** (roles `admin` and `support`, `USER_WRITERS`): `POST /v1/admin/users/:id/sign-out` (revokes every session, returns `{signed_out}`; agent keys are separate), `POST /v1/admin/users/:id/unlock-login` (clears the login-failure counter so a locked person can sign in), `POST /v1/admin/wallets/:id/revoke-key` (clears an agent key; the owner can issue a new one). **Admin only** (`USER_ADMINS`): `PUT /v1/admin/users/:id/status` and `PUT /v1/admin/wallets/:id/status` with `{status: "active"|"suspended"}` (a suspended person or wallet is refused on its next request, including agent keys; the default wallet cannot be suspended from the page; nothing is deleted). All actions sit behind confirm modals; every one is logged in `logs`.
- **Transactions rows open** (main Transactions page and the Transactions tab of a user and of a merchant, one shared `TxRowPair`): clicking a row (or Enter) slides open a detail line across all columns: `Transaction ID: <id> • COMPLETED` (or `• PENDING › awaiting_approval`, `• FAILED › <reason code>`) and, under it, `sender › receiver` with 32 x 32 photos (initials when none) that link to the user or merchant page (only for roles that can open them). The photos are built only after the first open. The reason code is no longer printed in the row itself (Funding-tab rows still print their failure code). API: each transaction (main feed, user and merchant) carries `from`/`to` names and `from_party` / `to_party` = `{id, kind: user|merchant, photo}` (null for the store and for the bank on a load, shown as "Bank"; photo only when it is an image address).
- Transactions period filter: `GET /v1/admin/transactions?from=YYYY-MM-DD&to=YYYY-MM-DD` (inclusive program dates in America/New_York; a day is 00:00 to 24:00 New York time, so daylight-saving days are 23 or 25 hours; either end optional; 400 for a bad date or from after to) applies to the list, the cards' `counts` and the new `totals` (`completed_count`, `completed_volume` of the chosen kind and period). The portal's Period select: All Time (default), Today, Yesterday, Last 7 Days, Last 30 Days, This Month, Last Month, Custom Range.
- Admin lists: `GET /v1/admin/merchants?q=` and `GET /v1/admin/users?q=` (name/handle(/email) filter, LIKE wildcards escaped, newest first, max 200; merchants carry balance, terminals, completed payments and volume; users carry balance, wallets and agent-wallet counts), `GET /v1/admin/transactions?kind=all|sends|taps|funds|agents&limit&cursor` (newest first, cursor `<ts>|<id>`; returns a `counts` object for every kind; taps = pay with a tag or pass; agents = sends/payments from wallets of type `agent`). Stats `payments.agents` (and `today.agents`) is a memo of agent-wallet sends and payments already counted in sent/tapped/in-app, so it is not added to the total.
- Tag pages (admin portal, UI says "tag" for the database's tag_models): `/tags` lists cards (click opens `/tags/<id>`; the last card is Add Tag); the tag page shows a static copy of the card plus Sales Ranking (`rank` = 1 + models with more sold, equal sales share a rank), Activated (tags assigned to a wallet), Provision Tags (button showing PENDING = max(0, quantity - tags loaded); opens a modal that reads the supplier CSV in the browser, extracts 14-hex UIDs, dedupes, and posts them in batches of 5000 to `POST /v1/admin/tag-models/:id/tags`) and Edit (the same modal as Add a Tag, titled Edit Tag, image optional). API: `GET /v1/admin/tag-models/:id` (model + `tags, unassigned, activated, pending, rank, models_total`), `PATCH /v1/admin/tag-models/:id` (partial; 409 `quantity_below_sold`, 409 `type_locked` once tags are loaded or units sold).
- Portal house style: the "selected or hovered" look is the opposite of the page via the `--pop-*` CSS variables (white on dark pages, black on light pages): never hard-code white or black for it; every page sets the tab title "<Page> · Nuclear Admin" via `usePageTitle` (the tag page uses the tag name); Copy buttons turn into "Copied" (shared `CopyButton`, no separate notice; the merchant portal must reuse it when built); Access Token / Access ID always capitalised; every button reads "Abc Def" and every status is UPPERCASE (global CSS); confirmations are modals; secrets are masked with Copy and Download; photos are uploaded, never URLs.
